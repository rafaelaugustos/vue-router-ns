## Predictive cancellation startup

The predictive suite now uses the same token-based native-start acknowledgement already used by the contract suite in #216. Only cancellation inputs wait for the fresh PID/sequence token on the app's next turn after its first public gesture observation. The existing five-second deadline and native progress, identity, history and reset-transform assertions remain intact. There is no manufactured callback, progress value, gesture replay or runtime change.

Android 16's [callback dispatcher](https://android.googlesource.com/platform/frameworks/base/+/android-16.0.0_r1/core/java/android/window/WindowOnBackInvokedDispatcher.java) initializes its motion tracker during native Back startup and resets the start position on the following move. Its [touch tracker](https://android.googlesource.com/platform/frameworks/base/+/android-16.0.0_r1/core/java/android/window/BackTouchTracker.java) clamps inward displacement to zero. A delayed start can therefore leave a cancelling input with events but no positive progress. The controlled experiment reproduces that mechanism; it does not measure the exact queue delay of the hosted failure.

With an isolated 650 ms delay in the fixture's first callback, the previous driver failed with 28 zero-progress events. The corrected driver passed all 15 legacy reports and observed positive progress. Both compared runs used ADB36.0.0 and the same delayed APK. A mismatched token failed at the five-second acknowledgement deadline. The final build without the delay passed all 15 reports as well. The [startup inventory](evidence/native-matrix-recovery/startup-validation.json) includes exact patches, APK hashes, raw reports and excluded diagnostics. Both APKs were inspected for the acknowledgement code; only the diagnostic APK contains the delay. The committed source contains no artificial delay.

Two earlier local runs stopped when ADB disconnected during screenshot collection; they are not counted as passing suites. A later fault-injection probe encountered a second interrupted read and correctly failed instead of retrying indefinitely. The original successful probes and hosted 34/35 probes remain separate evidence.

The Android workflow now includes `verify-system-ui-recovery.mjs` after its positive legacy controls. It disconnects only the selected emulator's ADB transport during the dump and requires a real partial-read failure, identity verification and an unchanged fixture report. It cannot pass if no interruption occurred.
